# P1 学习笔记：记忆、工具调用与图片

> P0 是"能聊天"，P1 是"能记得、能查、能看图"。这一层的难点不在 API，而在**上下文怎么组织**和**错误怎么兜**。

## 1. function calling 到底发生了什么

它不是"模型去调用了你的函数"，而是三件事的循环：

1. 你在请求里放 `tools: [{type:'function', function:{name, description, parameters}}]`，等于递给模型一份 API 文档。
2. 模型决定要调，就返回一条 assistant 消息，带 `tool_calls: [{id, function:{name, arguments}}]`——注意 **arguments 是一个 JSON 字符串，不是对象**，模型可能写错。
3. 你执行完，把结果作为 `{role:'tool', tool_call_id: 那个id, content: 结果文本}` 塞回历史，再请求一次。模型看到结果，才继续说话。

关键细节，踩过才知道：

- **回填时 assistant 那条必须带 tool_calls 一起放回去**，否则模型不知道"这条 tool 结果是回答哪一次调用"。agent.js 里那一行 `messages.push({role:'assistant', content: text || null, tool_calls: calls})` 就是干这个的。
- **content 为空时要给 null**，给空字符串有的 provider 会报参数错。
- **流式下 tool_calls 是碎片**：同一个 index 分多帧，id 和 name 只在第一帧出现，arguments 是一段段字符串拼起来的。llm.js 的 mergeToolCalls 按 index 归并，缺 id 时补一个，这是最容易写错的地方。
- **一次可能返回多个工具**（同一轮的 calls 数组），要按 index 顺序逐个执行。
- **循环必须有上限**：maxRounds 用完后，最后一轮不再传 tools，逼模型用已有信息回答。否则模型可能无限"再搜一次"。

## 1.5 补的两刀：日期与引用

第一次验收「今天有什么新闻」时，她只调了一次搜索、搜索词写的是「2025年」，回答全是比喻没有事实。两个原因都在 prompt：

1. **模型不知道今天几号。** 训练数据有截止时间，不说日期它就只能猜年份。现在 system 里固定带一节【现在的时间】（Intl 按 Asia/Shanghai 格式化，每轮现算），搜索词立刻变成「2026年10月27日 今日新闻 头条」。
2. **人设的「短」和「别像客服」把事实挤掉了。** 加了【工具与事实】一节：用了工具就要说清谁/什么事/什么时候、末尾单独一段给 1~2 条来源、链接只能来自工具结果、查不到就说查不到。

改完再测：搜了两次（今日头条 + 国际新闻），回答是「以色列今天在投票选总理…」「美国暂停中国公民去北马里亚纳免签…」并附两条来源。这说明**工具能不能用是工程问题，愿不愿意说人话是 prompt 问题**，两者要分开调。

## 2. 上下文窗口怎么组织

每轮发给模型的东西按顺序是：

    system（人设四层 + 记忆块）
    few-shots（5 组示例问答）
    最近 N 轮原文（memory.recentTurns）
    本轮用户输入

三条上限互相配合，缺一条就会失控：

| 参数 | 作用 | 默认 |
|---|---|---|
| maxTurns | 原文攒到多少条触发摘要压缩 | 40 |
| keepRecentTurns | 压缩后保留最近几条原文 | 12 |
| maxPromptFacts | 记忆块里最多放几条事实 | 12 |
| maxPromptChars | 记忆块总长度硬上限 | 1200 |

**记忆块并进同一条 system 消息**，而不是另开一条 system。原因很实际：各家对多条 system 的容忍度不同，合并最省事。

**为什么不干脆全塞进去**：40 条原文 + 事实 + few-shot 大约 3~5k token，每轮都付这个成本；而且越长的上下文，模型越容易忽略中间部分（lost in the middle）。摘要压缩是把"旧账"从逐字变成梗概，用信息密度换 token。

## 3. 摘要压缩与"会淡忘"

摘要 prompt 的写法比模型选择更重要，我们的规则是：

- 保留：对方透露的事实、双方的情绪变化、没聊完的话题、约定过的事
- 丢掉：寒暄、重复、你自己的具体措辞
- 第三人称、200 字以内、只输出摘要正文

压缩时会把**上一次的摘要一起喂进去**，让它合并而不是覆盖——否则每压缩一次，更早的记忆就真丢了。

"会淡忘"用两套机制实现，都很便宜：

1. **指数衰减**：每条事实有个 strength，每轮乘 0.97；低于 0.15 就删掉。经常被重新提到的事实会被 remember 工具或抽取重新写入，strength 回到 1 ——相当于"常想起的事记得牢"。
2. **摘要只留最近一份**：更早的细节自然被压成梗概。

没有用向量检索，是刻意取舍：这个量级（几十条事实）不需要 embedding，关键词命中 + 全量放进 prompt 反而更可控，也符合零依赖。

## 4. 工具设计的三条纪律

1. **错误不抛给用户，回喂模型。** 搜索没配 key、网页打不开、参数写错，全部变成一句文本返回给模型，让它自己决定是道歉、换个说法再搜、还是直接说不知道。agent.js 里所有 catch 都在做这件事。抛给前端只会变成一条红色气泡，模型根本没机会补救。
2. **结果必须截断。** 一个网页正文可能几万字，直接塞回历史会瞬间吃满上下文。fetch_url 限 6000 字，agent 再兜一层 4000 字。
3. **外部输入是敌意环境。** fetch_url 是模型可以指定任意 URL 的工具——模型可能被网页内容诱导去读 `http://169.254.169.254/latest/meta-data`（云上元数据）或本地服务。所以 assertPublicUrl 挡掉 localhost / 10. / 172.16-31. / 192.168. / 169.254. / .local / file:。这类"模型决定去哪"的接口，边界检查必须写在代码里，不能写进 prompt。

另外：**工具描述就是给模型看的 API 文档**。写清楚"什么时候该用"比写清楚"参数格式"更能提升调用率，比如 web_search 的描述里明确"需要最新信息、确定不了的事实"。

## 5. 图片走另一条通道

视觉模型（glm-4v-flash）不支持工具调用，所以图片消息不进 agent 循环，而是直接单轮：

- 前端把图片读成 data URL（限制 2MB），随 `{sessionId, message, image}` 发出
- 服务端把最后一条 user 消息的 content 换成数组：`[{type:'text'},{type:'image_url', image_url:{url: dataURL}}]`
- 模型按 `vision.provider` 路由，与会话模型分开配

这样"能看图"和"能查资料"在同一只会话里共存，各自走最合适的模型。

## 6. 用固定测试集判断有没有退化

调 prompt 最怕"感觉变好了，其实别的地方坏了"。P1 的固定检查清单（每次改记忆/工具逻辑都过一遍）：

| 用例 | 期望 | 怎么看 |
|---|---|---|
| 今天有什么新闻 | 日志出现 `[chat]` 前有 tool=web_search，回答带链接 | curl 看 tool 事件 |
| 我叫阿龙 | 隔 5 轮问"我叫什么"仍答得出 | /persona 页导出记忆，看 facts |
| 一条无关闲聊 | 不触发工具，不写事实 | facts 数量不变 |
| 发一张图 | meta.model 变成 visionModel | SSE 第一帧 |

自动化能覆盖协议层（109 个用例），**"她记得吗、她查得对吗"只能靠这套人工清单**——这也是 P2 之后做简单回归集的起点。

## 7. 调试手册（P1 增量）

    # 看工具是否被调用、参数对不对（tool 事件是独立一帧）
    curl -sN -X POST http://127.0.0.1:8787/api/chat \
      -H 'content-type: application/json' \
      -d '{"sessionId":"debug","message":"今天有什么新闻"}'

    # 导出这份会话的记忆（原文/事实/摘要）
    curl -s 'http://127.0.0.1:8787/api/memory?sessionId=debug' | node -e "..."

    # 清空
    curl -s -X DELETE 'http://127.0.0.1:8787/api/memory?sessionId=debug'

常见现象对照：

| 现象 | 原因 | 处理 |
|---|---|---|
| 模型死活不调工具 | 描述里没写"什么时候用" | 补 description 的使用场景 |
| 调了工具但参数是空的 | 模型把 arguments 写成空对象 | 工具里给出可读报错，让它重试；必要时参数写进描述 |
| 一直循环搜索 | 结果没解决问题，模型不停再搜 | 降 maxRounds；在工具结果里加"没有更多信息了" |
| 记住了不该记的 | 抽出闲聊当事实 | 收紧抽取 prompt 的三类范围，或改人工 remember |
| 记忆块太长 | maxPromptFacts/maxPromptChars 太大 | 调小，先删事实再删摘要 |

## 8. 这一阶段的设计取舍

- **每轮后台抽取事实。** 用户选了及时性：回复发完才跑（setImmediate），不增加首字延迟，但每轮多一次约 200 token 的小请求。省钱的替代方案是信号词触发，代价是漏掉隐性信息。
- **会话 ID 存在浏览器 localStorage。** 服务端不建账号体系，一个浏览器一个会话。换浏览器就是新会话——这在个人项目里够用，也避免了登录。
- **记忆文件 600 权限，损坏自动备份。** 记忆里有大量私人对话，和 .env 同级对待；JSON 坏了就改名 `.corrupt-时间戳` 再从空开始，绝不因为一个坏文件把服务拖挂。
- **后台任务与响应解耦。** 摘要和抽取都在 res.end() 之后跑，失败只写日志。用户不该为"记忆整理"多等 2 秒。
- **工具层接口隔离。** 搜索只认一个 endpoint + Bearer key，换博查/SearXNG 只改 web_search.js 一个文件——这也是 P2 里"B 站接口变动只改一个文件"的同一个思路。
