# P2c 学习笔记：功能开关、事件总线、心情与记忆时间线

> P1 是"能记得、能查"，P2c 是给这些能力**装开关、留出口、加情绪**。这一层的难点不在模型，而在**多一个能力不能让主链路多一份风险**。

## 0. 这一阶段多了什么

| 文件 | 职责 | 关键点 |
|---|---|---|
| src/events.js | 极简事件总线 | 监听者抛错不外溢；off 幂等 |
| src/features.js | 能力宿主（注册表 + 装配器） | 按 config.features 启停；出错只记日志 |
| src/features/settings.js | 开关判定的唯一入口 | 未声明 = 关闭 |
| src/features/mood.js | 心情：判定、落盘、注入 prompt | delta 而非绝对值；temperature 0 |
| src/features/memory-timeline.js | 记忆时间线页面 + 备份恢复 | 路由由能力自己注册 |
| public/memory.html | 时间线 UI | 置顶 / 删掉 / 备份 / 恢复 |
| public/index.html | 右下角心情挂件 + SSE 客户端 | 不用刷新就能看到心情变 |
| server.js | /api/events、能力路由分发、health 汇报 | 开关跟随热加载 |

## 1. 为什么先做开关，而不是先做功能

做 P2c 之前，任何新能力都只有两种接入方式：写进 handleChat 的 if-else，或者复制一份流程。两种都会让"关掉它"变成一件需要改代码的事——于是"关掉开关主链路行为完全一致"这条验收标准根本无从谈起。

所以顺序是反的：**先有一层能整体摘掉能力的装配机制，再往里塞能力**。这样：

- 出问题时第一件事是关开关，而不是回滚提交；
- 每个能力都能单独用一条"开关关闭"的测试守住主链路；
- 能力之间只能通过事件总线说话，不许互相 require（否则摘一个会连带摘不掉）。

## 2. 装配器：sync 只做差异，注册物归能力所有

`createFeatureHost` 不做"启动一次"这种事，它只提供 `sync(config)`：

```
sync(config)  ->  想要的状态 = module.enabled(config)
                  想要开 && 没在跑  -> start()
                  想要关 && 在跑    -> stop()
                  其余             -> 什么都不做
```

server 的 `resolveLive()` 每轮都会读一次配置（热加载），顺手调一次 `sync`。因为 sync 只处理差异，热加载开关就等于"改 config.json 的 features.enabled，下一句话生效"，不需要重启，也不会每个请求都重建定时器。

第二个设计点是**注册物归属**。能力 init 时拿到的不是共享 ctx，而是一层 `Object.create(context)` 的门面：

```js
scoped.route('GET', '/api/mood', handler);      // 记在 mood 名下
scoped.addPromptBlock(fn);                       // 记在 mood 名下
scoped.addAfterReply(fn);                        // 记在 mood 名下
```

stop 时按名字把这三类东西一起删掉。这样"关掉 mood"不需要 mood 自己写清理代码，也不会出现"路由还在、实现已经停了"的半死状态——那种状态最难受，因为请求能进来，但什么都不会发生。

第三个设计点是**出错只记日志**：

- init 抛错 → 状态记 `{ enabled: false, error: '原因' }`，路由清空，sync 不抛；
- prompt 片段抛错 → 只丢那一段；
- 回复后处理（异步）抛错 → 只 warn，请求早已返回给用户。

对照一下：如果能力 init 里抛的错能冒到 createServer，那"关掉 mood 就不会挂"这句话就是假的——因为配错一个参数就能让服务起不来。

`/api/health` 里 `features` 字段直接映射这套状态，排查时先看它，比翻日志快。

## 3. 事件总线：能力不直连渠道

需求是：主动搭话、B站分享都要"能推到网页，也能推到群"。如果让每个能力自己拿 res 或自己调渠道发送函数，代码会在"网页怎么收、群怎么发"上分叉两次以上。

所以中间加了一条总线：

```
能力  --emit('push', { target, text })-->  bus  -->  SSE 客户端（网页）
                                              \-->  群聊发送函数（P2e 注册）
```

两个细节值得记：

1. `emit` 里对每个监听者包 try/catch，并且先 `Array.from(set)` 快照。前者保证一个坏监听不吞掉整条事件，后者保证监听者在回调里 off 自己不会让 Set 在遍历中变形。
2. `on` 返回的 off 是**幂等**的。SSE 连接的 `req.on('close')` 和 `res.on('close')` 会都触发，幂等让"两处都调"变成安全的事。

SSE 端点 `/api/events` 本身不含业务：它只把总线上的 `mood` / `push` 转成 `data: {...}` 帧，每 25 秒发一个注释帧防中间层掐连接，断线就摘监听。网页端用原生 `EventSource`，一行都不用引库。

## 4. 心情系统：为什么用 delta，不用绝对值

让模型直接输出"现在心情 80 分"有两个问题：每次都是独立判断，数值会乱跳（上一轮 80、这一轮 20）；而且模型对绝对数值没有稳定标尺。

改成**增量**：模型只看"这一轮之后心情变化了多少（-5 ~ +5）"，服务端负责 `value = clamp(value + delta, 0, 100)`。好处是：

- 变化有惯性，语气是慢慢变的，不会一轮从委屈到狂喜；
- 判定的任务变窄了（只判方向和幅度），temperature 0 下更稳；
- 数值永远在合法区间，模型输出再离谱也污染不了状态。

档位（低落 / 有点丧 / 平静 / 心情不错 / 特别开心）由数值**推导**，不让模型给。这样只有一份真相：`data/mood.json` 的 `value`。否则模型可能返回"特别开心"配 30 分，注入 prompt 时自相矛盾。

几个"放在哪儿"的选择：

| 选择 | 原因 |
|---|---|
| 判定放在回复已经发给用户之后 | 判定是额外一次模型调用（几百毫秒到几秒），放在前面会拖慢回复 |
| temperature 0 + 强制 JSON + 容错解析 | 判定不需要创造力；解析器容忍代码块围栏和前后解释，解析失败就跳过本轮而不是记 0 |
| 只注入"档位 + 数值 + 最近 3 次原因" | 给模型情绪线索，但不给它一长串历史去推理 |
| prompt 里明说"不要报数值" | 不说的话她会写出"我现在心情 72 分"，一秒出戏 |

成本要说清：**开着 mood，每轮多一次 LLM 调用**。这就是为什么它必须是开关，而不是默认行为。

失败路径全都降级到"这一轮没有心情变化"：判定请求失败、JSON 解析失败、写盘失败，都只 warn。

## 5. 记忆时间线：置顶是最强的信号

P1 的记忆已经有强度衰减（每轮 ×0.97），问题是**用户没法干预**：想永久记住的记不住，想删的删不掉。

置顶的语义实现得很小：`pinned === true` 的事实

- 在 `decayFacts()` 里直接跳过衰减并把强度拉回 1；
- 在 `trimFacts()` / `factsForPrompt()` 的排序里永远排前面，所以"事实超过上限"时先被挤掉的是没置顶的。

一个字段同时解决了"不淡忘"和"不被挤掉"，不需要第二套存储。

备份用的是**纯 JSON 整包**（`{ version, exportedAt, sessions: [...] }`），不用 zip：零依赖项目里引压缩库不值当，而记忆体积本来就只有几十 KB。

恢复的两条讲究：

1. 同名会话先 `copyFileSync` 成 `.bak-时间戳`，覆盖是可以后悔的；
2. 结构不对的会话跳过并记进 `errors`，**不因为一条坏数据让整包失败**。恢复备份最怕的就是"因为一条脏数据，什么都没恢复成"。

页面上所有文本都用 `textContent` 写入，不用 `innerHTML`：事实内容是模型写的，属于不可信输入。

## 6. 调试这套东西的顺手命令

启动前确认开关读到了（会打印启停清单）：

```bash
node server.js
# [features] 已启用：mood、memory ／ 已关闭：无
```

看状态（比日志全）：

```bash
curl -s localhost:8787/api/health | python3 -m json.tool
```

看心情、手动造一个事件：

```bash
curl -s localhost:8787/api/mood
# 网页开着时，另一个终端也能直接看 SSE 流
curl -N localhost:8787/api/events
```

想验证"心情真的会影响语气"，最快的办法是手改 `data/mood.json` 的 `value` 成 5 或 95，下一句就能听出差别——不用等判定慢慢累积。

开关回归（每次改能力都该跑一遍）：

```bash
# 1. 关掉 mood，确认聊天完全照旧、prompt 里没有心情段
# 2. 打开 mood，连续聊 10 轮，看挂件曲线有没有起伏
```

## 7. 已知取舍与下一步

- **心情是全局的**，不分会话：人格只有一份，心情也就一份。真要按会话隔离，把 `data/mood.json` 换成 `data/mood/<sessionId>.json` 即可，接口不用动。
- **恢复备份没有鉴权**：和整个 Web UI 一样默认只绑 `127.0.0.1`。上公网前必须加登录，这条在 P2e 之前不能忘。
- **事实还没按用户维度分**：群聊里每个人的事实要分开存，这是 P2e（qq-bridge）的前置，届时按 `facts[].userId` 加维度，时间线页面也顺带加一列筛选。
- **speakUp / bili 只是注册表里的名字**：现在没有对应的模块文件，所以它们显示为"已关闭"；实现时只需新增 `src/features/speak-up.js` 并在 `defaultModules()` 里加一行。
- **测试**：`node --test tests/*.test.js`。Node 22 上直接写 `node --test tests/` 会把它当模块路径报 MODULE_NOT_FOUND，加 glob 更稳。
