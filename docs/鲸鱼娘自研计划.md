# 鲸鱼娘自研计划（v1）

> 本文档是方案讨论的结论，作为交给 CodeBuddy 的开发依据。WorkBuddy 侧只做方案与 review，不做开发。

## 1. 项目目标

自研一只蓝发鲸鱼娘（暂名「蓝色小肥鱼」），完全自持有、可自己调试学习：

| 项 | 结论 |
|---|---|
| 运行环境 | 开发期在 Mac；P2 部署到腾讯云轻量（2G 内存即可，目标 ≤4G） |
| 技术栈 | Node.js 18+，**零 npm 依赖**（只用内置模块：http / fs / fetch / crypto 等） |
| 核心功能 | 网页私聊 → 记忆 → 联网搜索 → B站分享 → 群聊渠道（微信暂缓、QQ 双路线） |
| 模型接入 | OpenAI 兼容协议：主力 DeepSeek；VLM 用智谱免费档（glm-4v-flash）；预留 custom provider 接中转站 |
| 人设 | JSON 文件承载，改完即生效（不重启），参考 whale_gril 的 `/persona` 思路 |
| 参考项目 | [whale_gril](https://github.com/Banan1cee/whale_gril)（结构与功能蓝本，注意其微信桥是 Windows 专属，不复用）；[Yuuyuko-uu 的 DSH 插件](https://github.com/Yuuyuko-uu)（B站子代理 / 鱼的记忆 / 心情系统，作为架构模式融入） |

**关键动机**：不做 whale_gril 的直接使用者，而是参考其模块划分自己实现，所有能力升级为基于 function calling 的 agent 架构（这是 whale_gril 没有的），同时作为学习 AI 的载体。

## 2. 总体架构

```
渠道层     网页私聊(Web UI·SSE流式) │ 群聊桥(P2: QQ官方bot / NapCat·OneBot11) │ B站定时任务
              │
核心服务    Node.js 零依赖单体：server.js(HTTP/SSE/静态页/事件分发)
            ├─ 触发判断（群聊：@/被叫名才响应，6 分钟热度衰减）
            ├─ persona.js（人设 prompt 组装，读 personas/*.json）
            ├─ agent 调度（工具调用循环）
            └─ 回复后处理（拆成 2~3 条短消息、去句号波浪号）
              │
能力层      记忆系统（事实抽取+群聊摘要） │ 联网搜索 │ B站子代理 │ 心情系统
              │
外部 API    OpenAI 兼容 chat completions（DeepSeek/智谱/中转站）│ 搜索 API │ B站公开接口
```

核心原则：**渠道只是消息进出的适配器，全部接到同一个核心会话管线**；能力层一律做成模型可主动调用的工具（tool use），而不是 if-else 规则。

## 3. 已定技术决策（ADR 摘要）

1. **零 npm 依赖**：降低供应链与审计成本，代码全部可读可学。HTTP 服务用 `http` 模块，出站请求用 Node 18+ 全局 `fetch`。
2. **模型切换可配置**：`config.json` 中 `providers` 支持 deepseek / zhipu / custom 三份并存，`active` 一键切换；chat 与 vision 模型分开配。`config.json` 与 `data/`（记忆、聊天记录）**不进 git**，只提交 `config.example.json`。
3. **微信暂缓**：个人微信无官方机器人接口，所有路线（UI 自动化/协议）均违反微信条款且 whale_gril 的桥是 Windows 专属。P2 渠道阶段改做 QQ 双路线。
4. **QQ 双路线**：
   - **官方机器人**（q.qq.com 开放平台）：个人主体可建，群聊/单聊场景已开放；完全合规，但内容审核严、上线需提审、链接域名需 ICP 备案白名单。作为合规兜底。
   - **NapCat / OneBot 11**（dsh-qq-bridge 同款路线）：个人小号变机器人，体验最自然；有低但非零的违规风险，用小号自担。
5. **云上不跑本地模型**：2G 内存服务器只跑 Node 服务（约 100–200MB 常驻）；Ollama 本地推理只作为 Mac 上的学习/实验项，通过 custom provider 接入即可，无需专门适配。
6. **安全底线**：服务默认只绑 `127.0.0.1`；将来上云如需公网访问 Web UI，必须先加登录鉴权。人设内置安全底线条款（拒绝色情/歧视/诅咒/暴力威胁，简短拒绝不说教）。

## 4. 分期计划

### P0 地基（Mac 跑通网页私聊）—— 建议规模：最小可跑

**交付物**
1. `server.js`：内置 `http` 服务器（默认 127.0.0.1:8787）——静态文件 + `POST /api/chat`（SSE 流式响应）
2. `src/llm.js`：OpenAI 兼容流式客户端（fetch + SSE 解析，兼容 DeepSeek / 智谱 / custom；异常时返回可读错误信息）
3. `src/persona.js` + `personas/whale.json`：人设 JSON（identity / style / bottomLines / mood / fewShots 分字段），每次请求现读，改完即生效
4. `public/index.html`：聊天页，多气泡展示（模型回复按换行拆气泡）、流式打字效果
5. `config.example.json` + `.gitignore`（忽略 `config.json`、`data/`）

**验收标准**
- 不执行任何 install，`node server.js` 即可启动；浏览器对话为流式输出
- 切换 `active` provider 无需改代码；key 未填时有明确中文报错
- 修改 `whale.json` 保存后下一句话即用新人设

**学习点（边做边讲，每项产出一段讲解笔记进 `docs/`）**：OpenAI 兼容协议的消息结构；SSE 流式格式与逐段解析；temperature 对人设聊天的影响；人设 prompt 的分层写法（identity/style/few-shots 各自作用）。

### P1 大脑（记忆 + 工具调用）

**交付物**
1. `src/agent.js`：function calling 循环——模型可调用工具，结果回填后再生成最终回复
2. 工具：`web_search`（搜索 API，候选：博查 / Tavily / Bing API，选型时对比免费额度）、`fetch_url`（网页正文抽取）、`remember`（写记忆）
3. `src/memory.js`：三层记忆——短期（近 N 轮原文）→ 事实抽取（用户自报的名字/喜好，带时间戳）→ 会话摘要（超过阈值后压缩，参考「鱼的记忆」的会淡忘设计）
4. VLM 接入：图片消息走智谱 `glm-4v-flash`（免费）
5. `/persona` 简易调参页（改人设/语气/长度）

**验收标准**：问「今天有什么新闻」时模型自主调搜索并引用来源；自我介绍后隔多轮仍被记住；记忆文件可导出/清空。

**学习点**：function calling 协议与工具循环；上下文窗口管理；摘要压缩的 prompt 技巧；如何用固定测试集做简单回归评估（判断记忆/搜索是否退化）。

### P2 渠道与部署

> 本节是 P2 的原始范围。实际分批与验收以「P2 扩展」节的分步顺序（P2c → P2d → P2e）和第 6 节里程碑表为准；下面与「QQ 官方机器人」相关的内容已降级为**可选路线**（NapCat/OneBot 11 为主路线）。

**交付物**
1. QQ 官方机器人适配器（WebSocket/回调 + 官方 API 发消息）——**可选，不参与里程碑验收**
2. NapCat/OneBot 11 适配器（HTTP 事件 + 发消息，同一路线可日后扩展其他 OneBot 端）
3. 群聊触发逻辑：@/叫名响应、6 分钟连聊窗口、防刷屏；回复拆条
4. B站定时分享（子代理模式，参考 dsh-bili-subagent）：定时拉热门/指定 UP 视频 → 子代理读标题字幕挑选 → 用蓝色小肥鱼口吻生成评论 → 推送到网页/群；频率默认 180 分钟，可关
5. 心情系统（参考 dsh-feiyu-mood）：每轮结束让模型自评心情值，存 JSON，织入下轮 prompt，Web 页右下角可见
6. 腾讯云部署：`systemd` 常驻（零依赖项目不需要 pm2）；日志轮转；防火墙只开必要端口
7. **密钥上云方案（ADR）**：systemd `EnvironmentFile=/etc/whale-girl.env`（root:root 600）注入 `WG_*` 环境变量；配置读取优先级约定为 `环境变量 WG_* > config.json > config.example.json`，云上 config.json 的 key 字段留空。密钥不进项目目录、不写 shell rc 文件；云服务器普通用户无权读取 env 文件本身。本地 Mac 开发仍用 config.json。现阶段不引入 KMS/SSM

**验收标准**：QQ 测试群（NapCat 路线）里 @ 蓝色小肥鱼 3 轮内稳定回复；服务器重启后服务自动拉起、记忆不丢。（B站分享的验收见 P2d；心情系统的验收见 P2c；官方机器人路线不参与验收）

**风险与对策**：QQ 官方线上审核不通过 → 该路线本就可选，直接放弃、只留 NapCat；NapCat 风控 → 用小号 + 控制发言频率；B站接口变动 → 接口层隔离，失效只改一个文件。

### P2 扩展：功能开关框架 + 五项 DSH 式能力（参考 Yuuyuko-uu）

#### 功能开关框架（先做，是其余能力的前置）

1. **配置结构**：`config.json` 顶层加 `features` 节，每个能力一个对象，形如 `{ enabled: false, ...参数 }`；未声明的能力视为关闭。开关跟随现有 `hotReload` 机制，改完下轮生效。
2. **集中装配**：新增 `src/features.js` 作为注册表——每个能力是一个模块，统一导出 `{ name, enabled(config), init(ctx), stop() }`；server 启动时逐个装配，`/api/health` 汇报各开关状态，日志打印「已启用/已关闭」清单。
3. **隔离原则**：单个能力初始化或运行失败只记日志、绝不能拖垮聊天主链路；每个能力模块有独立测试文件。
4. **主动推送基建（前置）**：新增事件总线 `ctx.emit('push', { target, text })`——网页端通过全局 SSE 广播通道接收；群聊渠道（P2 渠道适配器）注册发送函数后也能收。bili-subagent（以及后续若恢复的 speak-up）都走这条通道，不自己直连渠道。

#### 验收标准（每项能力）

- 关掉任一开关，主聊天链路行为与之前完全一致；`/api/health` 正确反映开关状态
- mood：连续聊 10 轮，挂件数值有涨跌且语气可感知变化（人工判定）
- （后续）speak-up：冷却时间内绝不重复触发；安静时段零打扰——本期不交付，验收项保留备用
- bili：能稳定产出「小鲸口吻」的分享（字幕拿不到的视频按跳过处理、不重试不报错）
- qq：测试群 @ 3 轮内回复；非白名单群完全静默；记忆与网页会话不串

## 7. 2026-10-29 决策与落地记录

> 这一节是当天的收敛结果，供以后学习与重构对照；细节分别在 `docs/业务需求说明书.md`（业务）、`docs/P2f-方案-插件化.md`（技术）、`docs/P2d-扩展-B站智能体.md`（B站）、`docs/心情表现方案.md`（心情）、`docs/M4-E2E验收清单.md`（验收）。

### 7.1 能力分层

- 能力分两层：**核心能力**（核心对话与人设、记忆、心情、系统管理、外部能力管理）随宿主常驻、不可卸载；**外部能力**（B站智能体、QQ群聊智能体）走插件化，可安装/禁用/卸载，故障不影响核心。
- 网页定位为**旁路渠道**：会话固定 `main`，管理端随宿主启动、能对话并实时接收她的主动播报；本期不做外部形态的「网页对话能力」。
- B站没有开放平台企业资质，账号相关能力（历史/关注/互动/消息）只能走登录态网页接口，失效即降级为公开浏览。
