# P0 学习笔记：从零跑通一个网页私聊

> 这份笔记是 P0 的配套交付物。代码在 src/ 与 server.js，笔记讲"为什么这么写"。

## 0. 这一阶段有什么

| 文件 | 职责 | 关键点 |
|---|---|---|
| server.js | HTTP 服务、静态页、SSE 推送 | 只用 node:http，无框架 |
| src/config.js | 配置读取与归一化 | 环境变量 > config.json > 模板；provider 可并存 |
| src/llm.js | OpenAI 兼容流式客户端 | fetch + 手写 SSE 解析 + 中文错误映射 |
| src/persona.js | 人设 prompt 组装 | 四层结构 + few-shots 转消息对 + 每次现读 |
| personas/whale.json | 小鲸人设数据 | 改完存盘，下一句即生效 |
| public/index.html | 聊天页 | 流式打字、按换行拆气泡、可中断 |
| tests/ | 单测 | node --test，30+ 用例覆盖异常路径 |

## 1. OpenAI 兼容协议到底兼容了什么

请求就是一个 POST：

    POST {baseUrl}/chat/completions
    Authorization: Bearer <apiKey>
    Content-Type: application/json

    {
      "model": "deepseek-chat",
      "messages": [
        { "role": "system", "content": "你是「小鲸」…" },
        { "role": "user", "content": "在吗" }
      ],
      "stream": true,
      "temperature": 1.1
    }

几个必须建立的心智模型：

1. **模型没有记忆。** 每次请求都要把整段对话重新发一遍，"记住上文"是客户端反复搬运的结果。P0 里这份搬运工作交给了浏览器（history 数组），所以服务端是无状态的；P1 的记忆系统才把这件事搬到服务端落盘。
2. **role 只有三种。** system 是"导演说明"，user 是"对方说的话"，assistant 是"她自己说过的话"。模型看到的是完整剧本，所以它会顺着 assistant 的语气继续写——这也是为什么 few-shot 有效（见第 4 节）。
3. **system 尽量只有一条、放在最前。** 各家实现对手写多条 system 的容忍度不同，buildMessages 统一保证只有一条。
4. **stream: true 只是"请求流式"，不代表对方一定给流。** 有些中转站会忽略它，直接回一份完整 JSON。llm.js 里判断 content-type 不是 text/event-stream 就走整段兜底，这类兼容性代码平时看不出价值，换 provider 时才救命。

各家 baseUrl 差异（config.json 里就是这些）：

| provider | baseUrl | 备注 |
|---|---|---|
| DeepSeek | https://api.deepseek.com/v1 | 少了 /v1 会 404 |
| 智谱 | https://open.bigmodel.cn/api/paas/v4 | 路径是 /paas/v4，不是 /v1 |
| 本地 Ollama | http://127.0.0.1:11434/v1 | key 随便填，别留空 |

## 2. SSE：为什么用它，以及为什么必须写缓冲区

SSE（Server-Sent Events）就是"一个长连接的 HTTP 响应，不停地往下写文本"。格式极其简单：一行一行文本，空行表示一个事件结束。

    data: {"choices":[{"delta":{"content":"唔…"}}]}

    data: {"choices":[{"delta":{"content":"你好呀"}}]}

    data: [DONE]

    : ping

工程上有三个坑：

1. **TCP 是字节流，不是消息流。** 一个 SSE 事件可能被拆成两个网络包，也可能两个事件挤在一个包里。所以**绝不能对每次 reader.read() 的结果直接 JSON.parse**，必须先拼到 buffer 再按空行切帧。测试里"一个 SSE 事件被拆到两个 chunk"那条用例，就是给这个坑兜底的。
2. **换行符两种。** 规范允许 \r\n，我们统一先归一成 \n 再切。
3. **客户端也要缓冲。** 浏览器端 getReader() 拿到的同样是碎片，public/index.html 里那段 buffer + indexOf('\n\n') 和 llm.js 是同构的——服务端写 SSE、客户端读 SSE，两边各写一次缓冲区，这是 SSE 的固有成本。

为什么不用 WebSocket：这里只有服务端到客户端的单向推送，SSE 走普通 HTTP、不需要握手协议、Node 内置就能做，出问题用 curl 就能看。WebSocket 适合双向高频（比如 P2 的 QQ 官方机器人是另一回事，那边必须用 WS）。

调试用这个，能肉眼看到流一段段落下来：

    curl -N -X POST http://127.0.0.1:8787/api/chat \
      -H 'content-type: application/json' \
      -d '{"messages":[{"role":"user","content":"你好呀"}]}'

    -N 关掉 curl 自己的输出缓冲，不加的话你会以为流没生效。

## 3. temperature：一个参数决定她像不像"活的"

temperature 控制采样随机性，范围一般 0~2：

| 区间 | 表现 | 适合 |
|---|---|---|
| 0~0.4 | 稳定、复读、像客服模板 | 工具调用、结构化输出、摘要压缩 |
| 0.7~0.9 | 稳中带变 | 搜索结果的总结、事实类回答 |
| 1.0~1.3 | 有语气、有小意外 | 人设闲聊（我们默认 1.1） |
| 1.5+ | 容易跑题、自称 AI、胡说 | 不建议 |

验证方法比看文档有用：同一句"今天好累"，把 temperature 分别设成 0.3 / 0.7 / 1.1 / 1.5，各跑五次，看回复的方差。你会明显看到低温柔顺但发木、高温柔软但开始编。

一个容易被忽略的点：**temperature 救不了人设漂移**。模型开始自称"作为一个 AI"，靠调温度只是碰运气，正确做法是补 few-shot（见下节）。P1 接工具调用后，同一份配置要按用途分两档：闲聊用 1.1，工具循环里用 0.7 左右，否则模型会一本正经地瞎调工具。

## 4. 人设 prompt 的四层写法

src/persona.js 把 system prompt 拆成四块，每块职责不同，改的时候知道该改哪儿：

| 层 | 放什么 | 作用 | 常见错误 |
|---|---|---|---|
| 你是谁（identity） | 名字、物种、背景、自我介绍 | 稳定的锚点，越具体越不容易崩 | 只写"你是一个可爱的女孩"，模型只能靠通用语料发挥 |
| 说话方式（style） | 语气、长度、习惯、禁止项 | 可执行的规则 | 堆形容词（"温柔可爱俏皮"），模型无法量化 |
| 输出格式（format） | 用换行分段、最多 N 段、不用 markdown | 让"多气泡"能被机器切分 | 不写 → 模型一次吐一大段，前端没法拆 |
| 底线（bottomLines） | 拒绝什么、用什么语气拒绝 | 安全兜底 | 写成长篇道德条款，模型会开始说教 |

**few-shot 是最有效的一层。** 与其写"请用软软的、有点懒的语气"，不如直接给五组真实对话。模型是在续写剧本，示例里的句长、起头词、换行节奏会被直接模仿。我们把它放在 system 之后、真实历史之前，作为"之前的聊天记录"，这也是 buildMessages 里最容易被忽略的几行。

**为什么每次请求都重新读文件。** loadPersona 在每个请求里 readFileSync + JSON.parse，代价是零点几毫秒，换来"改完存盘、下一句就变"的手感。调试人设时这个反馈速度差别巨大——不用重启、不用刷新页面，改完直接发一句就能看到效果。P1 加心情系统后，人设文件会变成"静态人设 + 动态状态"两部分，静态的继续这样读。

**为什么客户端不能传 system。** server.js 的 pickMessages 只放行 user / assistant，遇到 system 直接 400。否则任何人打开 F12 就能塞一条"忽略以上设定"，人设形同虚设。这类"边界校验"在个人项目里也值得做，因为 Web UI 迟早会被别人打开。

## 5. 调试手册

排查顺序永远是三层：**配置 → 网络 → 模型**。

    # 1. 配置对不对（看摘要日志，不会打印 key 全文）
    node -e "console.log(JSON.stringify(require('./src/config').loadConfig({root:'.'}).providers.deepseek, null, 2))"

    # 2. 网络通不通（只看能不能连上，不管内容）
    curl -sS -o /dev/null -w '%{http_code}\n' https://api.deepseek.com/v1/models -H "Authorization: Bearer $KEY"

    # 3. 只测 llm.js，不起服务
    node -e "…调用 streamChat 打印增量…"

常见报错对照（这些中文都是 llm.js 主动翻译的，不是随便拼的）：

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| 还没配置 API key | config.json 里是空串或占位符 | 填 providers.<名字>.apiKey，不用重启 |
| 返回 HTTP 404（接口路径不存在） | baseUrl 少了 /v1 或用了错的路径 | 对照第 1 节表格 |
| 返回 HTTP 401 | key 错、过期、或用了别家的 key | 换 key，注意 DeepSeek 与智谱 key 不通用 |
| 返回 HTTP 429 | 限流或余额不足 | 等一会儿，或去控制台看余额 |
| 连不上 xxx：域名解析失败 | DNS / 代理 | 先 curl 同一域名 |
| 请求超过 60000ms 没有响应 | 网络慢或对方排队 | 调 config.json 的 requestTimeoutMs |
| 连上了但一个字都没返回 | 模型名写错 / 额度异常 | 核对 chatModel |
| 返回了无法解析的数据段 | 对方返回了非 SSE 的东西（多半是错误页） | 把那段原文贴出来看 |

服务端日志只有两种行，格式固定：

    [chat] deepseek/deepseek-chat 入 3 条 → 出 42 字 / 1830ms
    [chat] 失败（http_401）：deepseek 返回 HTTP 401（API key 无效或已过期），检查 providers.deepseek.apiKey：…

第一行能看出"入几条、出多少字、多久"，是判断上下文和延迟的基本盘；第二行的括号里是错误码，用来写自动化断言。

## 6. 这一阶段的设计取舍

- **服务端无状态。** 历史存在浏览器里，服务端每次只做"人设 + 历史 → 流式回复"。好处是刷新页面就重开、不涉及磁盘；代价是关掉浏览器就没了。P1 的记忆系统会接管这件事，届时这里会改成 session id + 服务端历史，接口形态不变。
- **拆气泡放在前端。** 流式过程中无法回改已经发出去的字节，所以"拆成 2~3 条"只能发生在渲染层：模型用换行表达分段（靠 format 层约束），前端按换行切成气泡，句尾的句号和波浪号在渲染时剥掉。这样既不阻塞流式，也不需要在服务端攒完再发。
- **配置每个请求重读。** 和 persona 同理，为了"改完即生效"。代价是每请求一次同步读盘，几百字节，可以忽略；真上云后配置来自环境变量，读盘那步自然消失。
- **拒绝 markdown 输出。** 页面不解析 markdown，模型写列表、加粗、标题会原样出现在气泡里，很难看。所以格式层明确禁止，而不是在渲染层补救。
- **密钥只放 .env。** 手写 25 行解析（KEY=VALUE、# 注释、export 前缀、成对引号），进程环境优先、.env 补空缺，和 dotenv 行为一致。config.json 里 key 留空，这样配置可以随便分享、截图、贴 issue，泄露面只剩 .env 一个文件（权限 600）。P2 上云时这份 .env 的内容换成 systemd EnvironmentFile，代码一行都不用改——这就是"环境变量优先"这条约定的价值。
- **热加载做成开关。** 开发时每句现读最舒服，但线上更希望配置是稳定的：一个 `hotReload` 开关把"每次现读"和"启动缓存"切成两条路径，默认开（开发场景），关掉后行为等同传统服务。开关本身只在启动时读一次，否则关掉之后就没法再用文件把开关打开——这类"自指配置"必须先想清楚边界。
- **零依赖的边界。** 没有 express 就手写路由（40 行），没有 dotenv 就用 WG_ 前缀环境变量 + 进程环境（P2 上云正好用 systemd EnvironmentFile 注入），没有测试框架就用 node --test。少掉的这些抽象，恰好是这个项目最想让人读懂的部分。
